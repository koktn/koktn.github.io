# arXiv論文の日本語解説記事

arXiv論文を本文・図表・付録まで確認し、このプロジェクトの読者向けに正確で実用的な日本語記事を作る。

## 調査

1. リポジトリの`AGENTS.md`、`src/content.config.ts`、内容が近い既存記事を確認する。明示されたローカル規約を優先する。
2. arXivの最新版について、少なくともabstractページとHTML全文またはPDFを読む。abstractだけで記事を書かない。
3. 次の情報を本文、図表、付録から抽出する。
   - 論文の版、改訂日、著者、対象領域
   - 解こうとしている課題と既存手法の不足
   - 提案手法の構成、入出力、学習または処理フロー
   - データ、比較対象、評価指標、サンプル数、実験条件
   - 定量結果、統計的有意性、定性的結果
   - limitation、追加の注意事項、future work
   - 公開コード、データ、モデル、プロンプトの有無
4. 背景説明に追加資料が必要な場合は、原著論文、公式ドキュメントなど一次情報を優先して確認する。

具体的な論文や最新情報の確認にはWeb検索を使う。論文に書かれていない詳細を、一般知識や類似研究から推測して事実のように補わない。

## 内容の組み立て

見出し名や順番は論文に合わせて調整してよいが、記事全体で次を簡潔にカバーする。

- 課題
- 手法のポイント
- 検証方法
- 結果と効果
- 限界と、さらなる改善課題
- 実際に試す・実装するときの手順

冒頭で論文の価値を一文で要約し、LLMや対象分野に詳しくない読者にも用語を説明する。手法の関係が文章だけでは分かりにくいときは、小さな表、フロー、疑似コードを使う。

### 用語と文体

技術用語を機械的に日本語へ訳さない。対象読者がエンジニアの場合、原論文の英語表現、一般的なカタカナ、自然な日本語のうち、概念を最も直感的かつ曖昧なく伝える表記を選ぶ。

- `judge`を「審査器」、`deployment`を「配備」のように、不自然または別のニュアンスを生む直訳へ固定しない。
- phase名、component名、metric名、algorithm名など、原論文との対応が重要な語は英語を優先する。たとえば`Birth / Training / Deployment / Monitoring`、`judge`、`meta-judge`、`rubric`、`rationale`など。
- 初出で必要なら「rubric（評価基準）」のように短く補足し、以降の表記を統一する。
- 日本語として定着した語はカタカナでもよい。読者が意味を取りにくい英単語まで英語化しない。
- 原論文の用語と筆者が追加した実装上の用語を混同しない。

完成前に、独自componentやphaseを日本語へ直訳していないか、同じ概念に複数の訳語を使っていないかを全文で確認する。

数値は次を区別する。

- 相対改善と絶対改善
- オフライン指標とオンラインのユーザー指標
- 手法単体のablationとシステム全体の比較
- 相関・一致率と因果的な効果
- ベンチマーク上のクラス比率と本番の発生率

比較群、評価単位、期間、標本数、`p`値など、結果を解釈するために必要な条件を数値の近くに書く。論文が絶対値を公開していない場合は、グラフから精密な値を推定しない。「改善した」と「効果が証明された」を混同しない。

## 実装セクション

原論文の再現手順と、公開情報から導いた実装案を分ける。モデル名、プロンプト、評価基準、データが非公開なら、そのため完全再現できないことを先に明示する。

公開情報で可能な範囲に応じ、次の観点を具体化する。

- 最小構成のアーキテクチャとデータの流れ
- 入出力スキーマ
- データ収集、分割、ラベル付け
- 中核アルゴリズムの疑似コード
- ベースラインと評価指標
- 小規模検証から本番導入までの段階
- 費用、遅延、失敗時のフォールバック
- ログ、バージョン管理、ドリフト監視、ロールバック
- 安全性、プライバシー、人手レビュー

論文固有の値は「論文で採用された設定」と示し、別環境でも最適だとは断定しない。提案するサンプル数や閾値など、筆者側の実務案は論文の結果と明確に区別する。コードはベンダーに依存させる必要がある場合を除き、概念を移植しやすい疑似コードまたは厳密な型付き例にする。

## 出典とAI表示

記事冒頭に、構成と本文をAIが作成したことを明示する。人間による確認を実施していない場合は、確認済みとは書かない。

原論文のarXiv abstractページへのリンクを必ず掲載し、利用価値があればPDFまたはHTML版も併記する。他の記事や論文を内容上の出典として使った場合は、参照箇所または末尾の参照一覧から正確なcanonical URLへリンクする。検索結果ページへはリンクしない。原論文以外を参照していない場合は、その旨を記載してよい。

短い引用が不可欠な場合を除き、日本語で要約する。引用と自分の解釈を区別し、原文を長く転載しない。

## このプロジェクトへの保存

- 記事は`src/content/blog/`へ、内容を表す英語のkebab-caseファイル名で保存する。
- frontmatterは`src/content.config.ts`のschemaに合わせる。
- 新規記事は原則`draft: true`で作成する。公開依頼が同時に明示されている場合だけ`draft: false`にする。
- 日付はこの環境のタイムゾーンで確認する。
- 公開URLや画像はプロジェクト規約に従う。
- 既存記事の文体は参考にするが、不正確な表現や古い形式は引き継がない。

保存後、少なくとも次を実行する。

```sh
npm run check
npm run build
npm test
git diff --check
```

環境上のテレメトリ設定書き込みだけが検証を妨げる場合は、`ASTRO_TELEMETRY_DISABLED=1`を各Astroコマンドに付けて再実行する。下書きは本番ビルドから除外されるため、必要に応じて一時的な公開ビルドまたは開発サーバーで生成HTMLを確認し、最終状態を`draft: true`へ戻す。

表、コードブロック、長いURLがモバイル幅であふれないこと、ライト・ダーク両配色、見出しリンク、外部リンクを可能な範囲で確認する。ブラウザが利用できず目視確認できなかった場合は、その事実を報告する。

## 公開の境界

記事作成の依頼だけでは、コミット、push、公開を行わない。ユーザーが公開を明示した場合は、次を行う。

1. `draft: false`へ変更する。
2. 公開状態で全検証を再実行する。
3. 記事に関係するファイルだけを、短い命令形のsubjectでコミットする。
4. 現在のブランチとデプロイ設定を確認し、許可された範囲でpushする。
5. GitHub Pagesのworkflow完了と公開URLのHTTP成功を確認する。

既存の未コミット変更をコミットへ混ぜない。公開または外部更新に必要な承認は、実行直前に取得する。
